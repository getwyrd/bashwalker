# bashwalker

The origin of bashwalker is simple: I needed to inspect bash commands generated by an AI component and determine if there are commands that need human inspection or not. Another project of mine had very similar needs, bash evolves and has versions, so extracting that functionality as a more general use case seems obvious.  You can find more details in the [Architecture Description](https://github.com/getwyrd/bashwalker/blob/main/docs/design/architecture/01-introduction-and-goals.md)

A bash command line in, proven facts per simple command out: a fail-closed tree-sitter-bash walker (extracted from nl-shell)

```python
import bashwalker

walked = bashwalker.walk("cd /tmp && git push origin HEAD:main 2>/dev/null")
for invocation in walked.invocations:
    print([w.text for w in invocation.words], [w.literal for w in invocation.words])
# ['cd', '/tmp'] [True, True]
# ['git', 'push', 'origin', 'HEAD:main'] [True, True, True, True]
```

`walk()` parses a line with the pinned tree-sitter-bash grammar and returns one `Invocation` per simple command, including those inside substitutions, functions and here-doc command lines: its words (each marked literal or not), assignments, redirects and where its stdin comes from. `walked.untrusted` names any feature tree-sitter-bash reads differently from bash. A fact that cannot be proven comes back as the worst case (non-literal, `unknown` stdin, an untrusted tree), and a walk that cannot be completed raises `ParseRefused`. bashwalker makes no policy decision: what a command may do is the caller's to judge.

tree-sitter and tree-sitter-bash are pinned exactly, because every fact depends on how that grammar reads bash; pin bashwalker exactly for the same reason.
